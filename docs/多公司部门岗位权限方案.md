# 多公司 / 部门 / 岗位权限方案

_这是第 4 条需求的设计文档。动手前需要确认 3 个决定（见文末）。_

---

## 一、现状：为什么所有人看到同一份数据

查了库，8 张业务表里**只有 `create_by`，没有任何组织归属字段**：

| 表 | 现在的归属依据 | 应当归属 |
|---|---|---|
| `tz_plot` 地块 | 无 | 公司 |
| `tz_scouting_record` 巡田记录 | 无（经地块间接） | 公司（经地块） |
| `tz_follow_up_task` 复查任务 | 无 | 公司（经地块） |
| `tz_qa_session` / `tz_qa_message` 问答 | `user_id` | 公司（经用户）+ 本人 |
| `tz_market_price` 行情 | 无 | 公司 |
| `tz_supply_demand` 供求 | 无 | 公司 |
| `tz_knowledge_base` 知识库 | — | **全局共享，不隔离** |
| `tz_image_preset` 预置样张 | — | **全局共享，不隔离** |
| `tz_ai_call_log` 调用日志 | — | 管理员可见，不隔离 |

也就是说，**不是权限没配，是数据根本没有归属字段可依**。想隔离就得先加字段、回填、再改查询。

现有的可用骨架（若依原生，不必重造）：

- `sys_dept`：`100 若依科技 → 101 深圳总公司 / 102 长沙分公司 → 各部门`，天然是「公司→部门」两层
- `sys_role`：只有 2 个——`1 超级管理员(data_scope=1 全部)`、`2 普通角色(data_scope=2 自定义)`
- `sys_post`：`董事长 / 项目经理 / 人力资源 / 普通员工`
- RuoYi 的 `@DataScope` AOP + `dataScopeFilter`：能自动把数据范围拼进 SQL，**前提是表里有 `dept_id` 且 Service 方法加了注解**

## 二、目标模型

```
公司（sys_dept 的顶层节点，parent_id=0）
 └── 部门（sys_dept 子节点，可多层）
      └── 成员（sys_user，属于某个 dept）
           ├── 岗位（sys_post）：决定在组织里的角色定位
           └── 角色（sys_role）：决定能点哪些菜单与按钮、能看到多大范围的数据
```

**三个"不同"分别由什么实现：**

| 要求 | 用哪个机制 | 说明 |
|---|---|---|
| 同公司只能看本公司数据 | 业务表加 `company_id` + 查询按当前用户公司过滤 | 需要新增字段与改查询（本次主要工作量） |
| 不同部门权限不同 | `sys_role.data_scope` = 本部门 / 本部门及以下 / 自定义 | 若依原生，配一下即可 |
| 不同岗位权限不同 | 不同 `sys_post` 绑定不同 `sys_role` | 若依原生，需要新增几个角色 |
| 管理员例外 | `role_key=admin` 且 `data_scope=1` | 已有，保持 |

## 三、要做的四块

### A. 数据归属（新增字段 + 回填）

- 8 张业务表加 `company_id`（建议直接存顶层 `sys_dept.dept_id`）与 `dept_id`（可选，用于部门级权限）
- 存量数据：全部回填到一个「默认公司」，保证改完老数据不丢、老用户还能用
- 知识库 / 预置样张 / AI 日志**不加**，它们是全局共享的

### B. 查询过滤

- 各 Service 的 list 方法加 `@DataScope` 注解，Mapper XML 的 WHERE 里补 `${params.dataScope}`
- 需要走一遍 8 张表 × 增删改查的 SQL；`tz_*` 里所有跨表查询也要带上归属条件（比如"巡田记录列表"要 join 地块，过滤条件要落在地块的公司上）

### C. 公司与邀请（新增表与接口）

新增两张表：

- `tz_company` —— 其实可复用顶层 `sys_dept`，但公司级的联系人、规模、认证状态等字段 `sys_dept` 没有，单独一张表更清楚
- `tz_invite` —— 邀请码、目标公司、部门、岗位、角色、有效期、状态、被邀请人、发起人

接口大致：

```
POST /tz/company                创建公司（注册后的出路之一）
POST /tz/company/{id}/invite    生成邀请（需要"邀请成员"权限）
GET  /tz/invite/{code}          查看邀请详情（未登录可读，用于展示"谁邀请你加入哪"）
POST /tz/invite/{code}/accept   接受邀请 → 绑定部门/岗位/角色
GET  /tz/company/members        成员列表
PUT  /tz/company/member/{id}    改岗位或角色
DELETE /tz/company/member/{id}  移出公司
```

### D. 注册流程改造（现在的做法要废掉）

**现在**：注册 → 直接给 `role=2` + 默认部门 → 立刻能看到全部地块和记录。这就是你说的"极其不合理"。

**改成**：注册 → 用户建好，但 `company_id` 为空、**没有任何业务数据权限** → 登录后进入引导页，只有两条路：

1. 手上有邀请码 → 输入邀请码 → 加入对应公司的对应部门与岗位
2. 没有 → 申请创建新公司（创建者自动成为该公司管理员）

## 四、工作量与风险

- 涉及 8 张表结构变更、约 30 处 SQL、8 个 Controller/Service、新增 2 张表 + 1 套邀请流程、前端 3~4 个页面（引导页、公司/成员管理、邀请页）
- **风险点在于 B（查询过滤）**：漏掉一处，就会出现"能看见别的公司数据"的越权，而且从界面上完全看不出来。所以每一张表都要补一条回归用例，断言"切换账号看不到别的公司数据"

## 五、需要你定的 3 件事

1. **一个用户能否同时属于多家公司？**
   - 能（比如技术人员服务多个果园）→ 需要一个"当前公司"切换器，实现更复杂
   - 不能（一人一公司，最简单，也符合大多数企业内部系统的做法）

2. **创建公司要不要审核？**
   - 要（管理员在后台批准）→ 多一张待审列表和一个"系统管理"菜单
   - 不要（注册即可创建，创建者自动成为管理员）→ 快，但可能被滥用

3. **邀请方式用哪种？**
   - **邀请码/邀请链接**（把码发给对方，对方注册后填入）—— 无需邮件服务，最快落地
   - 邮件邀请（需配 SMTP）
   - 管理员直接建账号（不用邀请流程）

**我的建议**：一人一公司 + 免审核创建 + 邀请码。理由是这是**实训演示项目**，越简单越不容易出错，也最贴近你说的"只能通过邀请加入或创建新公司"。若你选别的，我按你的来。

确认后我按 A→B→C→D 的顺序做，每做完一块跑一次回归（184 项 + 新增的越权用例）。
