## 二、项目用途

**田诊助手（柑橘版）** —— 面向基层农技员与种植合作社的 AI 植保巡田报告助手。

一句话业务：**田间拍照 + 症状描述 → AI 诊断 → RAG 防治建议 → 结构化巡田报告 → 自动复查任务**。

- 用户：乡镇/区域农技推广人员、合作社负责人（**非**普通农户）
- 定位：课程 Demo 原型，柑橘垂直打样，**架构按多作物设计**（芒果/水稻已预置在字典里），
  扩展作物理论上只需补知识库数据
- 模块一（P0）：PC 后台 —— 看板、地块、巡田记录、AI 诊断/建议/报告、知识库管理
- 模块二（P1）：移动端 H5 —— 农技问答、行情查询、供求撮合（**注意：这是本项目唯一一处
  主动偏离 PRD 计划的地方**，PRD 原规划为微信小程序、2026.10 上线，实际提前用 H5 实现）

## 七、关键业务链路

### 7.1 分级诊断（`DiagnosisService.diagnose`）

用户永远拿得到东西，或者拿到明确拒绝——**不会凭空编一个结论**：

```
1. 预置映射   图片 MD5 命中登记样张 → 标准结论         → source=preset   （演示 100% 稳定）
2. 大模型初诊  读图 + 症状 + 知识库片段 → 结构化 JSON  → source=llm
              （置信度 < 60 不采信，转降级）
3. 关键词降级  知识库 bigram 检索，置信度上限 55       → source=fallback
4. 都不行     抛异常，明确说「补充症状或联系农技员」
```

每次结果都带 `source` + `degradeReason`，**前端标签明示**，不把降级冒充成 AI 结论。

> `useLlm=false` 可强制走保底路径，前端有开关。

### 7.2 检索阈值（`RagService`）

- 字段权重：病名 10 / 症状 4 / 发生条件 2 / 防治·用药·安全 各 1，病名完全命中额外 +50
- **采信双条件**：`MIN_SCORE=3.0` **且** `MIN_GAP=2.0`（第一名领先第二名 2 分）
- 为什么用分差不用倍数：检索串带「柑橘」前缀会给所有条目加一个近似常数分，
  常数会把倍数压扁（同一份证据 2.96 倍 → 1.50 倍），分差对常数偏移免疫
- 已知代价：简写但准确的描述（分差 1.75~1.91）会被**有意拒答**，空档很宽（0.45 → 1.75），
  **没有为了让数字好看调阈值**

### 7.3 剂量校验（`DosageGuard`）的一个坑

`%` 也在受管单位里，导致正文模板拼进去的「置信度 90%」曾被抹成「（用量待确认）」——
**拦错一个真用量是合规事故，把置信度改写掉同样是交付事故**。
修法是加语境排除：数值前字是「率」「效」或「置信度」时原样留下。
边界**刻意不认「度」**（「浓度 0.5%」是真的用量，必须继续受管），
由 `DosageGuardTest#doesNotTreatConcentrationAsRateContext` 钉住。

被拦截的用量**不出现在给农户看的正文里**，只在界面侧栏单独标记 + 写调用日志。
理由：正文会被报告整段引用，「已拦截」标签拦不住任何人。

### 7.4 照片自动生成描述（`ImageDescriptionService`）

巡田登记的次序被**倒过来**了：原来要求用户先手打症状描述才允许保存，现在是
**照片必填、描述由系统看照片先写一版、用户在它上面改**。

理由是这条流程最容易断的地方就在键盘上——蹲在树下敲三行症状描述，是最容易被跳过
的一步，而它偏偏是知识库检索的唯一依据。照片则是本来就要拍的。

```
POST /tz/record/describe-image?imageUrl=/profile/...&plantPart=1
  （按 imageUrl 而不是 recordId 取图：这个动作发生在记录保存之前，还没有主键）

1. 预置样张登记的描述  图片 MD5 命中且该样张登记过 symptom_text
                      → 直接用登记时人工写的那段观察记录        → source=preset
2. 多模态模型读图      chatWithImage（图按 base64 内联）→ 结构化 JSON → source=llm
3. 都不通              success=false + 说明原因，把输入权交还用户（不塞空文字进去）
```

几条刻意的取舍：

- **预置优先于大模型**，与 7.1 同一套纪律：演示场景对稳定性的要求高于对「智能」的要求。
  库里三条演示样张登记了描述，所以**不配 API Key 也能把描述填出来**。
- **提示词硬性禁止出现病名与用药**。拍照就出病名的话，「描述 → 诊断」这个先后顺序
  名存实亡：用户会以为系统已经诊断过，报告里也会混进来路不明的结论。
- 模型自报 `observable=false`（照片糊、没拍到植物）时**采信它并拒答**。一张糊照片
  能编出一段像模像样的症状描述，而那段描述会一路带进检索和报告。
- 描述会**压掉换行并截断到 500 字**：它占的是一行输入框，不是排版稿。

前端落点（`views/tianzhen/record/index.vue`）：`watch` 表单里的 `imageUrl`，
值一变就自动识别一次，用 `describedImageUrl` 把「新上传的图」和「编辑时回填的图」
区分开——后者不该触发，否则一打开修改弹窗就会覆盖掉用户上次存下来的描述。
描述框里已经有用户自己写的字时，覆盖前会先确认一次。

> 相关的库表变更见 `sql/tz_photo_describe.sql`（`tz_image_preset` 加 `symptom_text` 列 +
> 回填三条演示样张），可重复执行。

## 十、开发前必读的几条约定

1. **权限串必须与菜单 SQL 同名同量**。业务权限串全部以 `tz:` 开头，逐个都要在 `sys_menu`
   有对应行，否则 `v-hasPermi` 会把按钮**从 DOM 里摘掉**（不是禁用，是消失）。
   `test-api.py` 第 15 组会扫源码 + 遍历菜单树断言一致性——改了权限没改菜单 SQL 会直接失败。
2. **知识库 id 不能依赖 AUTO_INCREMENT**。种子 SQL 已显式写死 100–114；
   `tz_scouting_record.knowledge_id` 存的是固定值，一旦重载种子导致 id 前移，
   记录会挂到不存在的条目上，**且界面上完全看不出来**（建议是按病名再查一次的）。
3. **不要为了让指标好看调检索阈值**。改阈值属于产品行为变更，应单独验证。
4. **不要编造农技数据**。知识库用量来自特定年份、特定区域的推荐值，**不是法定值**；
   不同来源倍数可能不一致（咪鲜胺 600~1500 倍都有），项目按来源如实收录、不擅自取中。
5. **换大模型服务商要改四项不是一项**：`provider` / `base-url` / `vision-model` /
   `text-model` 必须同一家，只改 `base-url` 一定 404。
6. **不要用 `glm-4v-flash`**：不收 base64（只吃公网 URL，会 400），且输出上限 1K token
   装不下四段式 JSON。`glm-4.5-flash` 已下线，别写回旧 id。

## 十二、已知缺口与后续改动建议

**真实缺口（勿用演示数据掩盖）**
- **S4 行情当日更新率 ≥ 90% 未达成**：`tz_market_price` 数据全靠人工录入，**没接任何数据源**。
  要达成需确认数据源（农业部门公开行情 / 产区批发市场 / 第三方服务）并做定时抓取。
- **S2 建议采纳率 / S3 问答一次满足率未验证**：需要真实农技员试用样本，Demo 阶段不编数字。
- **演示图片是程序画的示意图**（图内印有「示意图·非真实病叶照片」）。
  正式使用必须换实拍照片并同步更新 `tz_image_preset` 哈希（重跑 `seed-demo.py` 自动重建绑定）。
- **炭疽病条目的出处相对弱**：该病检索结果里没有官方植保站《病虫情报》，
  只能引州级《农业灾害应急技术手册》与农技问答资料，已在该条 `remark` 标注。

**改动方向的自然落点**
- 接专业识别模型 → 只实现 `LlmClient` 接口即可，业务层零改动
- 扩作物 → 补 `tz_knowledge_base` 数据 + 字典，业务代码不含作物硬编码
- 检索升级为向量 → 替换 `RagService` 实现，调用方无感
- 行情数据源 → 新增 Quartz 定时任务写 `tz_market_price`

**明确不做（边界）**：自训 YOLO、语音输入、GIS 地图、在线交易/支付、
向量数据库、微信小程序本体。
